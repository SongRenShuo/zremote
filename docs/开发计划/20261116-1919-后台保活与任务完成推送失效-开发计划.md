# 开发计划：后台保活与「任务完成通知」后台投递失效

> 版本基准：main（探查时 HEAD `bdd1a34`；鸿蒙计划 `20261116-1434` 实施中，与本计划写集不重叠）
> 目标：查清并修复「应用切到后台后任务完成收不到推送，点进应用重连后才推送」的缺陷，让**后台产生的任务完成事件能在后台即时投递本地通知**，而不是滞后到回前台。
> 状态：已完成（2026-11-16 实施 D1+D3+D4，提交 `82d560b`；P0 裁定否决 D2/D5——JS 桥硬约束；真机 E2E 因设备离线 not run，见 §8 实施记录）
> 关联实现：D1 `lib/services/background_heartbeat.dart` + `event_observer.dart` 注入 `__zrKeepAliveTick` + `session_view.dart` 后台心跳/`zrBgSnapshot` handler；D3 `lib/services/notified_event_store.dart`；D4 l10n 文案。
> 关联：只读探查报告（2026-11-16，后台子智能体，证据全文见本文 §2）；V2 大版本计划（`20261115-0901`，P5 保活/通知设计）；鸿蒙保活缺口（`20261116-1434`）。

## 1. 现象与结论先行

用户现象：应用切到后台，任务完成后**没有收到推送**；手动点进应用、重新连接后，通知才补发出来。

**根因判定（证据链见 §2）：问题不在「通知显示」，而在「后台事件能否被产生并回传」。**

本 App **没有任何原生/服务端推送通道**（无 FCM、无厂商推送、无 `UNUserNotificationCenter` 远程注册）。所谓「任务完成通知」是 `flutter_local_notifications` 本地通知，而触发它的 `completed` 事件完全寄生在一条**进程内的 WebView 链路**上：

```
宿主页面 JS（注入 hook） → flutter_inappwebview callHandler('zrEvents')
  → Dart JS handler → _onBridgeMessage() → EventParser / StateDiffer
  → notifyFrom() → 本地通知
```

切后台后，保活前台服务 + WakeLock **只能保证 Dart 进程存活，不能保证 WebView 里的 JS 定时器 / fetch 轮询 / WebSocket 回调继续执行**。Doze / 厂商冻结 / WebView 后台节流会让注入 JS 停摆 → `completed` 事件根本没被观察到 → 没有通知。

用户「重新连接后才推送」与此完全吻合：回前台触发 `_onAppResume()` → `_manualReload()` 重载 WebView → 宿主下发全量快照 → `StateDiffer` 比对出 `running → completedSuccess` → **补发** `completed` 事件 → 此时才弹通知。事件是「回前台后才产生」的，不是「后台攒着没发」。

**判定**：这是**链路设计缺口**——「保活（进程存活）」与「后台事件 → 通知（事件观察与投递）」是两条独立链路，前者工作不代表后者工作。当前把完成通知完全押注在「WebView JS 在后台持续执行」这一未被任何原生机制保证的前提上，前提一旦不成立（Doze、厂商冻结、WebView 后台节流），通知即丢失。

## 3. 修复方向（P0 裁定后）

> **P0 裁定（2026-11-16，读真实代码后）：D2/D5 的技术前提不成立，已否决。**
> 全仓所有宿主数据访问都走 `RpcBridge.call()` → `LoopbackDispatchServer.push()` →
> **注入 WebView 的 JS 从 loopback 拉命令** → `callHandler('zrSvcResult')` 回传 Dart
> （证据：`rpc_bridge.dart:152-228`、`rpc_dispatch.dart:56-95`、`event_observer.dart:488-514`）。
> Dart 与 Android 原生**无法绕过 WebView JS 直接访问宿主任务状态**，因此
> D2（Dart 独立轮询宿主接口）、D5（原生后台直连宿主）均不成立。
> **唯一可行的根治方向是 D1**：保活进程存活期间，由 Dart 定时 `evaluateJavascript`
> 主动唤醒注入 JS 的轮询并拉一次宿主任务快照，经 `zrBgSnapshot` 回 Dart diff 出完成事件
> 并即时弹通知；D3（去重持久化）防多链路重复，D4（文案如实化）管理预期。
> 本轮按 D1+D3+D4 实施。下表保留原方向供追溯。

| # | 方向 | 要点 | 预期效果 | 待验证 |
|---|---|---|---|---|
| **D1** | 利用保活让后台 WebView JS 续跑 | 保活前台服务存活期间，用 Dart 定时 `controller.evaluateJavascript(...)` 主动触发 `zrPollRevive()` / 状态拉取，抵消 JS 后台节流；配合提高 `zrPollStart` 的 45s revive 上限 | 最小改动；若 WebView JS 后台可被唤醒，则完成事件仍走原链路，通知即时 | **关键未知**：后台 `evaluateJavascript` 在主流 OEM（小米/vivo/鸿蒙）是否稳定可执行；需在真机实测 |
| **D2** | Dart 侧独立状态轮询（不依赖 WebView） | 由 Dart 直接定期请求宿主 view-state 接口并跑 `StateDiffer`，与 WebView 观察解耦；需解决宿主接口地址 + 认证 token 的可访问性 | 根治「JS 停摆即丢事件」；后台投递最可靠 | 宿主 view-state 是否可在 WebView 外直接调用（`event_observer.dart:127-132` 截获的是 WebView 内 `POST /mobile-view-state`，跨域/认证待查） |
| **D3** | 事件持久化 + 回前台补发（体验兜底） | `event_feed` 落盘；后台事件不丢；回前台 reload 后统一补发未读完成通知，避免「事件彻底消失」 | 不解决「后台即时推送」，但保证不丢通知；与 D1/D2 可叠加 | 补发的去重/幂等（避免与 StateDiffer 补发重复） |
| **D4** | 电池豁免引导 + 文案如实化 | 强化「申请忽略电池优化」引导与失败提示；Android 文案补上「后台事件可能延迟」说明；iOS/鸿蒙维持现有声明 | 降低 Doze 冻结概率、管理用户预期 | 属产品取舍，需确认文案口径 |
| **D5** | 原生后台轮询 + 本地通知（Android 根治） | 前台服务内用 AlarmManager/前台定时直接拉宿主状态并投递通知，彻底脱离 WebView | 最强保障 | 改动最大，且依赖 D2 的接口可访问性结论；用户无服务端推送通道，仍非真推送 |

**推荐路径**：先 P0 实测确认 D1 可行性（改动最小、复用现有保活）；若 OEM 上不可行，再评估 D2 的接口可访问性决定走 D2/D5；无论选哪条，D3+D4 作为体验兜底与预期管理同批补齐。

- **P0 诊断读数**：真机切后台（熄屏 + Doze）期间 logcat 证明保活服务在跑、但 WebView JS 轮询停止；回前台 reload 后补发事件的时间线（对应 L16 的 VM Service / logcat 取证方式）。

## 8. 实施记录（2026-11-16）

### 8.1 P0 诊断结论

- 代码级证据（探查 + 复核）确认根因：完成通知完全寄生于 WebView 注入 JS 观察者；保活只保进程，不保后台 JS 执行；回前台 reload 靠 `StateDiffer` 全量快照 diff 补发，正是用户「重连后才推送」的现象。
- **架构裁定**：D2/D5 前提不成立（JS 桥硬约束，见 §3），否决；实施 D1+D3+D4。
- **真机走查（2026-11-16 20:00+，设备上线后补做）**：
  - 构建 debug APK 装入模拟器 `emulator-5554`（v2.0.3），远程宿主重连上线（LED 绿）后宿主页面完整加载、RPC 服务就绪（`checks summary: 41 method-ok / 0 no-svc`）。
  - **D1 心跳机制验证通过**：切后台后 logcat 见 `[zr-resume] lifecycle ... hidden → paused` + `[zr-keepalive] bg tick device=...` 每 20s 一次（45s 内 2 次）、应用进程存活、前台服务常驻通知（id=901 / zr_keep）正常；`[zr-keepalive] tick result=ok` 证明 `evaluateJavascript` 后台可执行、注入的 `__zrKeepAliveTick` 已注入并运行。
  - **JS→Dart 后台通道验证通过**：诊断期 `post('zrBgDiag', ...)` 经 `callHandler` 从后台 JS 回传到 Dart 并打出日志，证明 callHandler 在后台可用。
  - **关键新发现（根因坐实）**：在线态后台诊断 `diag={"hasReg":true,"hasSvc":true,"hasFn":true,"e5":"ChannelClient is disposed"}` —— 注入 JS 能找到宿主注册表与 `windowControllerService.listTaskList`，但调用时宿主抛 **`ChannelClient is disposed`**。即宿主在页面进入后台时主动 dispose 了它自己的原生 RPC client（省电），导致任何主动拉宿主状态的 RPC 都失败。**这是宿主侧后台限制，App 侧无法绕过**。
  - **端到端「后台即时推送」判定**：因宿主 client 后台 disposed + 宿主事件推送（WS/fetch）在后台停止，本环境下无法做到后台即时弹通知；可靠路径是 D3 去重 + 回前台 reload 后 StateDiffer 补发（用户原始现象的机制），D4 文案已如实声明"可能延迟"。

### 8.4 走查后结论与残留风险（诚实标注）

- **D1 的真实定位**：真机证实 `evaluateJavascript` + callHandler 后台均可用（D1 链路打通），但宿主 `ChannelClient` 后台 disposed 使 `listTaskList()` 主动拉快照失败。因此 D1 的"主动拉快照"当前在主流宿主后台下不会产出完成事件；它保留为"宿主 client 恰好存活时"的尽力增强，无害。可靠的通知保证落在 D3（不重复）+ 回前台补发（不丢）+ D4（文案如实）。
- **要真正做到后台即时推送**：需宿主侧配合（后台不 dispose client / 提供服务端推送），属跨端/服务端立项，非本 App 可独立完成（见 §7）。
- **OEM/Doze 差异**：本轮在 Android 模拟器（API 37）验证；小米/vivo/鸿蒙冻结策略更激进，未覆盖，结果不泛化。
- **平台覆盖**：iOS 无后台模式，按现有文案声明不适用；鸿蒙由 `20261116-1434` 单独跟进，本轮未动 `ohos/`。
