## 2.6 问题十六：账户直连任意设备（调研已判定可行，有边界）

**结论**：可行——**「任意设备」= 同一 zcode 账号下、已由桌面端注册过的设备**（设备记录是账号维度；手机不能凭空注册新设备）。

**证据**
- 契约：`GET /api/v1/remote/device` 返回当前用户设备数组（强制 JWT，实测无鉴权/伪造 JWT 均 401 空正文）；`POST /api/v1/remote/token {role}` 的 token 绑用户+角色、**不绑 SID**、60s 一次性 → 同账号可连任意已注册设备。
- 官方手机 Web 端 `/remote/v4` 已内建「无 sid → 账号设备列表」（`webRemoteControlEntry.ts`）。
- 本仓与 zcode-switch 均无 `remote/device` 调用（V2 计划 P0-8 未落地）。

**P1（本轮）**：新增 `lib/services/remote_device_client.dart`（`listDevices()`，请求头全套照 `zaiBillingHeaders` 口径防风控，形状容错 `sid|device_sid`/`mid|device_mid`/`name|device_name`/`app_version`）；账号保险库页加「从账户添加设备」入口 → 选设备（同 mid 去重）→ 构造 v2 `RemoteDevice`（baseUrl=`https://zcode.z.ai/remote/v4`）→ 写入设备库并可选打开会话；可选兜底「打开账户设备页（免 sid）」。
**P2**：按 MID 去重/旧 SID 接续、删除入口、多设备选择器。
**风险**：需全套请求头 + `X-Device-Mid` 防风控；桌面端须同账号并开远控否则列表空；SID 会因桌面重注册漂移。

## 2.3.1 问题十三：重置卡状态加载失败（已定论）

`QuotaClient.fetchResetCardStatus()`（`lib/services/quota_client.dart:1333-1348`）调 `usage-stats.getCodingPlanUsageSnapshot` **不带参数**；宿主契约要求 `preferredProviderId` 且必须为 coding-plan provider，否则抛 `no_bigmodel_api_key`（`usageStatsService.ts` → `bigmodelUsageQuotaProvider`）。该异常不被 `ResetCardUnsupportedException`（只认 no-method/no-services）捕获 → 冒泡到 `_refreshResetCard` 的 catch → `_resetStatusFailed=true` → 显示 `quotaResetCardStatusFailed`「重置卡状态加载失败」（`quota_page.dart:121,691-695`）。`useResetCard()`（`:1351+`）同病。
**修复**：复用 `loadEntitlementParams()` 的 provider 解析传参；无 entitle provider/未配置 → 视作**不支持**（隐藏区块），真实 RPC 错误才显示失败态。归入 **quota 车道**。

## 2.3.2 问题十四：工作区显示路径而非名称（已定论）

`lib/ui/automation_form.dart:987-995` 下拉项直接 `Text(candidate)`，而 `candidate` 是 **workspacePath 原文**（如 `F:\code\Java\...`）；候选来自 `board.automations/offPeak` 的 `workspacePath`（`:571-572`）。
**修复**：显示名优先取 `sessionIndexProvider` 里该路径对应的 `SessionState.workspace`（宿主给的工作区名，`event_observer.dart` 的 `workspaceBasenameOf` 同款），否则取路径 basename（`uri` 风格末段）；下拉 value 仍为路径。补单测（路径→名称映射、无映射回落 basename）。

## 2.3.3 问题十五：默认权限模式显示英文枚举（已定论）

`lib/ui/settings_page.dart:837-863`：副标题 `trailing: Text(mode)` 直接显示 `kBehaviorModes` 的原始值（如 `acceptEdits`），选项标签是 `m.toUpperCase()`（`:856`）——非中文。
**修复**：为每个 mode 增加中文标签（新增 l10n `settingsBehaviorMode*`），副标题与选项都显示中文，value 仍存原文（持久化兼容）。补单测（渲染中文、选择后持久化原文）。

## 2.4 问题十二：资产浏览「记忆」形状降级（已定论）

**根因**：`lib/services/assets_client.dart` 的 `_memoryOf(values)` 第一段循环要求 `value is List`——但 RPC 回包经 `_valuesOf` 解包后 `values` 就是**顶层数组本身**（元素是 `ProjectMemoryWorkspaceSummary` 的 Map：`{id,label,updatedAt,files[]}`），不是「数组里嵌数组」。于是第一段永不命中；`_docsOf(values)` 也只找 `workspaces|memories` 键（实际没有）→ 返回 `degraded: true` → UI 显示 `assetsTabDegraded`「响应形状不识别，已按空列表降级」（`app_zh.arb:3239`）。

**契约对照**（开源=官方）：`memoryService.listProjectMemories(): Promise<ProjectMemoryWorkspaceSummary[]>`（`packages/services/src/memory/memory.ts:60-24`，字段 `id/label/updatedAt/files[]`）——本仓 `_memoryOf` 的 `_strOf(['label','name','id'])` 与 `files` 字段其实都对，**只是入口形态判断错了**。

**修复**：`_memoryOf` 增加「顶层即数组」形态（元素为 Map 且含 label/name/id → 直接归一），保留 `{workspaces|memories:[...]}` 与 `data/result` 外壳兜底；补单测（数组形态 / 外壳形态 / 空数组 / 形状不符）。

## 2. 根因分析

### 2.1 问题八：连接诊断点击没反应

**定位结论（子智能体实测复现，以此为准）**：**顺序颠倒**——`_DiagnosticsTile.onTap`（`lib/ui/settings_page.dart:977-987`）**先 `request(device.id)` 再 `Navigator.pop()`**。Riverpod 3 的 `ref.listen` 是**同步派发**，`SessionView` 的回调（`session_view.dart:1248-1251`）立刻 `Navigator.push(DiagnosticsPage)`（`session_view.dart:954-974`，push 前无 await），紧接的那行 `pop()` 弹掉的正是**刚压栈的诊断页** → 设置页留在原地、无诊断页、无提示 =「点击没反应」。

**证据**
- `settings_page.dart:977-987`：`request(device.id)` → `Navigator.pop()`（顺序颠倒）。
- 反证：`toolbox_sheet.dart:404-407` 同功能入口是**先 pop 再回调**，工作正常。
- 消费者并非缺席：所有设备的 `SessionView` 在 `IndexedStack` 里恒挂载（`app_shell.dart:240-246`），故最初的「无人消费」假设**不成立**（已更正）。
- SDK 语义：`riverpod-3.3.2`（`element.dart:464-484/889-899/1422`、`provider_container.dart:759-768`）listener 同步执行；`flutter_riverpod-3.3.2`（`consumer.dart:525-546`）`listen` 存 `_listeners`；`navigator.dart:4994-4996/5046-5058` push 同步入栈、`5573-5592` pop 取 `lastWhere(isPresent)`。
- 实测复现：同构最小样例，A（现状顺序）`diagnostics=0 open=1`；B（先 pop 后 request）`diagnostics=1 open=0`。

**修复方向**：① 先取 `notifier` 局部变量 → `pop()` → `request()`；② `DiagnosticsOpenRequestNotifier` 加 `consume()`（参照 `state/claim_entry.dart` 的 `ClaimOpenRequestNotifier.consume`），命中即消费，未被消费时给 SnackBar 降级提示；③ 文案如实说明（`settings*`/`diag*` 新增 key）。
**次要**：`session_view.dart` 的 `_rpcBridge == null` 路径只弹不明显的 SnackBar（可选优化，非本次根因）。
**备注**：`lib/ui/data_manage_page.dart` 里没有「连接诊断」入口（用户指的是设置页「数据与诊断」分组，`settings_page.dart:944`）。

### 2.2 问题九：检查更新没有结果提示

**已确证（静态）**

- `_UpdateTile._check()`（`lib/ui/settings_page.dart:1019-1035`）：`UpdateChecker(...).checkLatest()` 的返回**三种情况同形**——`null` 既表示「无更新」，也表示「检查失败（DioException/形状异常被吞）」（`lib/services/update_checker.dart:22-66`），还可能是「版本解析失败」。
- `_update = null` → 副标题回退成 `settingsUpdateCheckSub`「与 GitHub Releases 比对版本」，**没有任何 SnackBar/Dialog/文案变化** → 用户感觉「检查了但没结果」。
- **第二个更严重的根因**：`UpdateChecker._releasesApi` 指向**上游仓库** `https://api.github.com/repos/pjpv/zremote/releases/latest`（`update_checker.dart:18`），而本仓自 v2.0.0 起在 `SongRenShuo/zremote` 发 Release → 读到的是上游（旧版本/404），结论错误或恒为「无更新」。
- l10n 现有 key：`settingsUpdateCheck/CheckSub/Checking/Available/OpenRelease`——**缺「已是最新」「检查失败」两种文案**。

**判定**：①结果三态被压成一态且无提示；②数据源指向上游仓库（`pjpv/zremote`）而非本仓（`SongRenShuo/zremote`）。

### 2.2.1 问题九补充证据（子智能体实测）

- `SongRenShuo/zremote` latest = **v2.0.1**（HTTP 200 / 0.86s）；`pjpv/zremote` latest = **v1.7.0**（200 / 1.59s）——两者网络均可达，故"永远无更新"确系仓库指错。
- `SongRenShuo/zremote` 是 `pjpv/zremote` 的 fork（parent=pjpv/zremote）；写死 pjpv 的链接还有 `settings_page.dart:1102`、`about_page.dart:14-15`。
- 测试只覆盖 `parseRelease`；`l4_widgets_test.dart:166` 仅断言入口文案。

### 2.3 问题十：额度消耗预警（需求，设计见 §3.3）

**调研已定结论**（`~/.zremote-e2e/quota-alert-requirement.md`）：

- **判据**：统一 `QuotaOverview.percentUsed`（`quota_client.dart:291`），逐 `PlanSlot` 判定、`primaryPlan` 为主；`remaining` 带单位不可比，仅进文案。通路 A 的 `ZrQuotaLimit.percentage` 已被 `normalizeHostSnapshot`（`:442-444`）当已用占比；bigmodel 用 `usage/currentValue` 推算（`:716-725`）、zai 用 `total/used_units`（`:616-633`）。
- **缺口**：`ZrNotifyCategory.quotaLow`（`notifier.dart:22,50`）、`NotificationPrefs.quotaLow`（默认 false）、设置页 tile（`settings_page.dart:743-745`）与 l10n「额度耗尽预警/占位（暂未启用）」（`app_zh.arb:3479-3484`）**均已占位但无任何发送方**——本任务即补发送方。
- **触发缺口**：额度仅在 `QuotaPage._refresh`（`quota_page.dart:69-101`）拉取，无后台轮询；zcode-switch 有 5min sweep（`main.js:938`）但无预警逻辑，可借鉴的只有 sweep 节拍。

### 3.3 问题十设计（额度消耗预警）

> 待子智能体调研报告（`~/.zremote-e2e/quota-alert-requirement.md`）回填；先列主控已定的骨架：

| 维度 | 初定方案 |
|---|---|
| 判据 | 取通路 A 归一化后的 `QuotaItem.percentUsed`（已用占比 0-100）与 `PlanSlot.percentUsed`；取最大者 |
| 阈值 | 默认两档：**80%（提醒）/ 95%（严重）**；可在设置页调（10~100，步进 5），全局开关默认**开**（仅本机有凭据且能取到额度时） |
| 去重 | 持久化「上次预警水位档 + 上次预警时间」；同档 24h 内不重复；跨档立即发；`nextResetTime` 后重置 |
| 通知 | 新增独立渠道 `zr_quota`（复用 `NotificationSpec`/`zr_done` 同构），payload `quota:<deviceId>`，点击直达额度中心 |
| UI | 额度中心顶部预警条（80% 黄 / 95% 红）；设置页开关与阈值滑杆；（可选）设备卡/工具箱徽标 |
| 降级 | 无 token/未配置/取数失败 → 不预警（不出噪音）；仅通路 A 有快照时也按 `percentUsed` 判 |
| 与自动领取 | 额度耗尽（≥100% 或无 remaining）时文案提示「可去权益中心领取」并给 action 跳领取页 |
