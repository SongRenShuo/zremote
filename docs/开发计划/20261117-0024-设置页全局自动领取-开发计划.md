# 开发计划：设置页「全局自动领取」总闸

> 版本基准：`feat/v23-claim-manual`（HEAD `359fb37`；上一轮 20261116-2341 未合流，本计划在其上叠加开发，合流顺序：claim-manual → claim-global）
> 目标：参考 zcode-switch 的全局式自动领取设计（单一开关管全部账号），在应用设置页新增**全局自动领取总闸**——一处开关控制所有设备的自动领取启停，无需逐台设备去会话页打开。
> 状态：实施完成（2026-11-17，分支 `feat/v23-claim-global`，提交 `31ebf3b`/`3ebcb1e`；定向 105 例全绿 + analyze 零问题，收口读数见 §9）
> 关联调研：zcode-switch `f342256`（上游已 pull）自动领取全局开关设计（结论并入 §2）；上一轮计划 `20261116-2341`（本计划的直接前置）。

---

## 1. 现状与结论先行

当前自动领取是**纯 per-device 模型**：每台设备一份 `ClaimAutoConfig`（持久化键 `zremote.claimConfig.<deviceId>`），开关只在各设备的领取页里，用户想全局开/关必须逐台设备点开。zcode-switch 的对应功能是工具栏一个 `auto_claim` 全局开关，驱动"逐账号"的自动轮循环——一个开关管全部。

本轮新增：**全局总闸**（默认开，见 §3 裁定）。语义为层级门控：

```
实际自动领取 = 全局总闸（默认开） && 设备开关（默认关）
```

- 全局关 → 所有设备的调度代理停表（零调用）、`runNow` 拒绝、领取页明确提示。
- 全局开 → 行为与现状完全一致（设备开关各自决定）。
- 设置入口不依赖设备会话（0 设备可达，L27 判据）。

## 3. 关键裁定：全局默认值 = 开

`ClaimAutoConfig.enabled`（设备级）默认关，但已有用户可能已在部分设备打开。若全局闸默认关且作为必要条件，升级即回归（已开设备全部静默停摆）。故**全局总闸默认开**：
- 老用户行为零变化；
- tile 副文案明确「总闸：关闭后所有设备停止自动领取」；
- 设备级默认关的语义不变（全局闸只是乘法门）。

## 6. 验收

- **核心场景**：①设置页关闭全局总闸 → 已开自动领取的设备代理停表（零调用）；重新打开 → 恢复；②领取页 auto 卡显示「全局已关闭」提示、「立即执行一轮」禁用；③设置页 tile 开关往返 → 持久化往返一致（杀进程重启保留）；④0 设备安装可直接在设置页操作该开关（L27）。
- **反向验证（S2）**：摘掉 agent 的 `_globalEnabled` 门，"全局关 → 停表" 用例变红；摘掉 G4 提示行分支，对应 widget 用例变红。
- **回归**：per-device 开关/静默时段/runNow/一键领取/阻断历史全部不回归（上一轮定向用例照跑）；保活/通知等其他设置 tile 不回归。
- **测试纪律**：定向以判据数收读数（S3）；收口前全量 `flutter test` + `flutter analyze` 零问题（S11）；注入 JS 不动（M0 不触发）。
- **平台**：纯 Dart/UI 层，三端共用，无平台分支。

## 8. 不在本轮

- 不做 zcode-switch 式"逐账号循环"重构（zremote 已有 per-device 调度代理，只加门控不加新循环）。
- 不做全局静默时段（静默时段保持 per-device，各设备时区/使用习惯不同）。
- 不做全局「一键领取全部设备」（跨设备批量领取涉及多会话并发，另立项）。
