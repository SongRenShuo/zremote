# 开发计划：一键领取「0/0/0」误导汇总与自动轮阻断根因修复（激活前置）

> 版本基准：main（探查时 HEAD `a5f7ed6`，v2.2.0 已发行）
> 目标：修两个用户实测 bug——①设置页「一键领取所有设备」显示「成功 0，失败 0，跳过 0 台设备」但设备明明在线且实际处理过（汇总误导）；②自动轮反复落「账号未配置套餐」「可领列表获取失败 RpcRemoteException(call#N: Chan…)」阻断历史，而同账号 zcode-switch 功能正常。
> 状态：已完成（2026-11-18，主分支直接实施，提交见 CHANGELOG；定向 115 例 + 全量 1260 例全绿 + analyze 零问题，读数见 §9）
> 关联调研：zcode-switch `claim.rs`/`lib.rs` 只读对照（2026-11-18 主控探查，证据见 §2）；zremote 代码级根因（§3）。后台探查（宿主 event 服务可达性）进行中，结论并入 §4 裁定。
> 关联：`20261116-2341`（阻断历史/一键领取初版）、`20261117-1230`（单层总闸/全局一键）、LESSONS L39（宿主后台 dispose ChannelClient）、L18（能力态与业务态分离）。

## 1. 现象与结论先行

| # | 现象（用户实测截图） | 初步判定 |
|---|---|---|
| P1 | 设置页点「一键领取所有设备」→ SnackBar「成功 0，失败 0，跳过 0 台设备」，但设备 HQZC-01 在线（绿灯） | 汇总语义缺陷：设备实际被处理但结果被吞成 0/0（见 §3.1） |
| P2 | HQZC-01 领取历史 6 条全是阻断：「账号未配置套餐」（19:01、00:04）、「可领列表获取失败 RpcRemoteException(call#N: Chan…）」（17:55、19:40、20:49、22:36） | 两类根因：**缺激活前置**（服务端未"看到活跃"不出可领套餐）+ **宿主后台释放通道**（L39 已知限制）；同账号 zcode-switch 正常（见 §2） |

**根因判定（先说结论）**：
1. **P1 是 P2 的下游表现**：一键领取对该设备执行了，但 `fetchPreviews` 抛「账号未配置套餐」异常被 `catch` 吞成 `claimed=0/failed=0`，汇总三数字全 0，错误详情（reason）没有出口。
2. **P2 的「账号未配置套餐」不是账号真没套餐**——zcode-switch 同账号能看到可领套餐，差异在 zcode-switch 每次 preview 前先上报**激活事件**（`app_launch` + `app_daily_active`），服务端"看到活跃"后才返回可领套餐；zremote 依赖宿主页面自身上报，后台/未活跃时服务端无激活记录 → `manual_claim_preview_missing_data`。
3. **P2 的「可领列表获取失败 Chan…」是宿主后台限制**（L39）：切后台后宿主 dispose 自己的 `ChannelClient`，自动轮的后台 preview RPC 必然抛 `ChannelClient is disposed`——已知不可绕过，但当前 1h 去重窗口外仍每轮落一条阻断历史，且文案没告诉用户"前台打开页面即恢复"。

## 2. zcode-switch 对照（为什么它正常）

| # | zcode-switch 实现 | 证据 |
|---|---|---|
| Z1 | **激活事件前置**：`claim_refresh` 在 `preview_plans` 之前调 `report_activation_events(user_id, device_mid)`——POST `https://zcode.z.ai/api/v1/event/report`，依次上报 `app_launch`、`app_daily_active` 两个事件；失败仅记 `activated=false + activation_error`，**不阻断预览** | `src-tauri/src/lib.rs:232-249`（claim_refresh 先激活后预览）、`claim.rs:130-131`（URL 与事件常量）、`claim.rs:187-208`（report_activation_events） |
| Z2 | 事件体完整字段：`event_id(uuid)/client_timezone/client_language/element_name(事件名)/event_region:"app"/event_type:"view"/event_text/event_extra_detail/user_id/screen_resolution/app_version/device_os_category/device_os_version/device_mid/mac_id/marketing_params` | `claim.rs:158-180`（activation_event_body） |
| Z3 | user_id 从本地凭据解密取（`oauth:<provider>:user_info`），device_mid 为每账号持久化虚拟设备号 | `claim.rs:133-155`（telemetry_user_id）、`store.rs:1121` |
| Z4 | 直连 HTTP（ureq）+ 官方客户端头仿真（`X-ZCode-App-Version`/`X-Platform`/`X-Device-Mid` 等，`quota.rs:199-220`） | `claim.rs:130`、`quota.rs` 头构造 |

zremote 与它的差异：zremote 不走直连 HTTP（通路 A 宿主 RPC 是唯一通道，L37 判据），宿主页面的激活上报行为不受 App 控制——**这是功能差异的架构根源**。

## 3. zremote 根因证据（代码级）

| # | 事实 | 证据（文件:行号） |

| 3 | UI 只展示三个数字，无 per-device 详情出口 | `lib/ui/settings_page.dart`（_ClaimBatchButton snackbar） |

## 4. 修复方案（F1–F4）

| # | 内容 | 关键裁定 |
|---|---|---|
| **F1** 一键领取汇总如实化（P1） | ①`ManualClaimRunner.fetchAndRunAll` 捕获 `ClaimPreviewMissingData` → 返回 `(0,0)` + 设备级标记 `noPlans`（对齐自动轮"干净收轮"语义）；②hub 的 catch 分支把异常设备 `failed += 1`（或新增 `errored` 计数）并保留 reason；③汇总结果增加 per-device 明细，SnackBar 文案改为分档呈现（成功 N / 失败 M / 无券 K 台 / 未就绪 S 台），至少不再出现误导性全 0；④`claimAllLive` 的设备清单改用 `await DeviceStore.instance.loadAll()`（磁盘真值），修复"首次 read 到空列表 → 0/0/0"的第二触发面（§3 #8） | 纯 Dart/UI 层，无架构风险 |
| **F2 激活前置（P2 主根因）** | 三方向裁定（探查已完成 2026-11-18）：**A. 宿主 RPC 触发激活——不可行**：注入 JS 宿主服务注册表（`event_observer.dart:218-226`）与 17 个 channel 别名表（`rpc_bridge.dart:103-128`）均无 event/telemetry 服务。**B. 直连 HTTP 上报激活事件——可行性大增（推荐）**：探查确认 `event/report` 请求**只有 `Content-Type` 一个头、无 Authorization**（zcode-switch `claim.rs:200-202`），服务端靠 body 里 `user_id + device_mid` 关联账号——**不需要 JWT/token**；所需材料：①`user_id`（账号凭据里的用户 id，zcode-switch 从 `oauth:<provider>:user_info` 解密取 `id`，`claim.rs:135-156`；zremote 账号库凭据缓存是否含此信息待 P0 核对）；②`device_mid`（每账号持久化虚拟 uuid，zremote 可仿 `store.rs:1121` 生成存 device_store）。**C. 兜底指引**——missing_data 的阻断/汇总文案改为明确指引（"请在电脑端 ZCode 打开页面活跃一次，或用 zcode-switch 刷新后重试"）。**推荐：F2 先落 C（无条件）+ B（直连激活上报，最小子集，不碰 billing）**；上报失败静默不阻断预览（对齐 zcode-switch `activated=false` 语义） | P0 剩余核对：①zremote 账号库凭据缓存里有没有 user_id（账号库存的键集核对）；②真机实测——直连上报一次后 missing_data 是否消失；③上报频率/风控评估（仅两个埋点事件，频率 ≤ 每轮一次） |
| **F3 阻断分类与降频（P2 次根因）** | ①preview 异常 detail 含 `ChannelClient is disposed` → 新增阻断原因 `hostBackgroundUnavailable`（宿主后台已释放通道），落史降频（6h 窗口或同类只保留最新一条），文案「宿主后台已释放通道：前台打开设备页面后自动恢复」；②`manual_claim_preview_missing_data` 阻断文案加指引（联动 F2-C）；③阻断历史 UI 对重复同类显示"最近一次 + 次数"而非逐条堆叠（可选） | L39 已定论宿主侧限制，如实文案 + 降噪 |
| **F4 汇总/历史的可观测性** | 领取历史 blocked 条目在详情里展示完整 reason（当前 `RpcRemoteException(call#115: Chan…` 被截断）——长文本可展开；一键领取结果与阻断历史语义对齐（无券 ≠ 失败） | 小改动，随 F1/F3 同批 |

## 6. 验收

- **F1**：①设备无券时一键领取 → SnackBar 明确显示「无券 K 台」（非 0/0/0）；②RPC 异常设备计入失败/错误档；③反向验证（S2）：摘掉 MissingData 捕获，无券用例变红；④provider 空列表场景（冷启动直接进设置页）一键领取仍能遍历到设备（loadAll 兜底）。
- **F3**：①含 `ChannelClient is disposed` 的 preview 失败落史为 `hostBackgroundUnavailable` 新原因，6h 内不重复；②文案含恢复指引；③既有 blocked 历史渲染不回归。
- **F2（若 B 落地）**：真机实测——激活上报后 preview 从 missing_data 变为返回套餐列表（zcode-switch 同账号已验证该链路有效）；上报失败不阻断预览（activated=false）。
- **回归**：单设备手动领取、自动轮开关/静默时段、一键领取互斥、阻断历史渲染、领取通知不回归。
- **测试纪律**：定向以判据数收读数（S3）；全量 `flutter test` + `flutter analyze` 零问题（S11）；注入 JS 不动（M0 不触发）。

## 7. 风险

| 风险 | 缓解 |
|---|---|
| R1 直连激活上报涉风控（头仿真/频率） | 仅上报激活事件（非 billing），频率跟随 preview（≤每 10min 一轮）；头模板照搬 zcode-switch 已验证实现；上报失败静默不阻断 |
| R2 JWT 获取链路不稳（凭据缓存缺失/过期） | 取不到 JWT 时静默跳过激活前置，回落 F2-C 指引文案；不新增失败路径 |
| R3 宿主 event 服务其实存在（探查发现） | 若 P0 探查发现宿主可调的激活服务，优先走通路 A（不引入直连），B 降为备选 |
| R4 阻断降噪过度（真失败也被吞） | hostBackgroundUnavailable 仅匹配 `ChannelClient is disposed` 精确文本；其他异常照常落史 |
