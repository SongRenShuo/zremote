# 开发计划：包名迁移至 `cn.song.zremote`（与上游应用共存）

> 版本基准：main（commit `3db62bc`）
> 目标：把 Android `applicationId` 由 `com.pjpv.zremote` 改为 `cn.song.zremote`，使本仓构建与上游 `pjpv/zremote` 的正式签名包**同机共存、互不覆盖**，并消除自定义深链 scheme 抢注。
> 状态：已完成（2026-11-16，本地全量 1183 例全绿 + analyze 零问题 + 构建 badging 确认 `cn.song.zremote`）
> 关联：上游签名调研结论（上游 release APK = 正式证书 `CN=ZRemote,O=pjpv,C=CN`，RSA-2048，v2 scheme；私钥只在上游 GitHub secrets，无法复用，见会话记录）；工作树 `zremote-wt/pkg-*`。

---

## 1. 背景与决策

**为什么不能沿用原包名**

- Android 判定「同一个应用」只看 `applicationId`，不看签名：**同 `applicationId` + 不同签名 → 第二个装不上**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），要么卸载要么覆盖，**无法共存**。
- 上游 `pjpv/zremote` 的 release APK 是正式签名（`CN=ZRemote,O=pjpv,C=CN`），私钥仅存上游仓库 secrets，任何外部人都读不到（GitHub secrets 不可读出明文；仓库历史/全部分支/Release 资产均无 `.jks`/`key.properties`）→ **签名不可复用**。
- 因此要让「上游包」与「本仓包」同机装，唯一可行是**换 `applicationId`**。

**决策**

| 项 | 决策 |
|---|---|
| 新包名 | `cn.song.zremote`（用户指定） |
| 共存原理 | `applicationId` 不同 → 系统视为两个独立应用；签名相同/不同都互不覆盖 |
| 签名 | 本仓沿用现有构建签名（自建/CI），**不与上游对齐**——独立任务，见 §6 |
| 自定义 scheme | `zremote://import` → **`zrsong://import`**（避免与上游抢注同一 scheme） |
| scheme 兼容 | 解析层**同时接受** `zremote://import` 与 `zrsong://import`（旧链接/上游下发链接不失效） |
| App Links | **保留** `https://zcode.z.ai/remote*`（不 `autoVerify`，是官方主通道） |
| iOS | `PRODUCT_BUNDLE_IDENTIFIER` 同步改 `cn.song.zremote`（保持一致；iOS 为未签名 ipa，不影响 Android 共存） |

**已知取舍**：保留 App Links 后，点击 `https://zcode.z.ai/remote*` 链接时系统会列出两个应用（未 `autoVerify` 的固有歧义），用户可选「始终」。若后续要求零歧义，再评估去掉 App Links 或改 `pathPrefix`（见 §6，不在本轮）。
