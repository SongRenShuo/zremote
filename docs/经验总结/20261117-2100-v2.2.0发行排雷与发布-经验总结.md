## 2. release workflow 的四连坑（按发生顺序）

### 坑 1：publish 被 iOS 容量取消拖死（L49）
- 现象：`publish.needs: [verify, apk, ipa, hap]`，ipa 在 macOS arm64 上**连续 3 次**跑约 15 分钟后被外部取消（非代码错误，`continue-on-error` 对「取消」无效），publish 直接 skipped → Android/鸿蒙资产明明构建成功也发不出去。
- 定位：查 run 的 job 列表，ipa `conclusion: cancelled`、publish `skipped`；apk/hap/verify 全 success。
- 修复：`publish.needs` 去掉 ipa 改 `[verify, apk, hap]`；`ipa` 加 `continue-on-error: true`；IPA 产物下载/重命名/`ls` 全部条件化（找不到就 warning 跳过）。

### 坑 2：鸿蒙产物路径写死（L53）
- 现象：hap 腿签名步骤 `-inFile build/ohos/outputs/default/ohos-default-unsigned.app`，实际产物在 `build/ohos/app/`（日志 `✓ Built build/ohos/app/ohos-default-unsigned.app`）→ `hap-sign-tool` 报 `11017001 Read zip file failed`。
- 修复：`UNSIGNED=$(find build/ohos -name 'ohos-default-unsigned.app' | head -1)` 运行时定位；`upload-artifact` path 改 `build/ohos/**/ZRemoteX-ohos-*.app`。

### 坑 3：artifact 带目录层级，下游扁平匹配漏（L51）
- 现象：publish 里 `ls artifacts/ohos/ZRemoteX-ohos-*.app` 报 No such file——因为 artifact 保留了 `build/ohos/app/` 层级，下载后是 `artifacts/ohos/build/ohos/app/...`。
- 修复：下游统一 `find artifacts/ohos -name 'ZRemoteX-ohos-*.app' | head -1`；IPA 同样改 `find`；末尾 `ls` 容忍 ipa 目录缺失。

### 坑 4：GitHub Release 不接受 `.app` 扩展名（L50）
- 现象：Android apk 同批上传成功，`ZRemoteX-v2.2.0-ohos.app` 报 `Validation Failed: name has a file extension that is not allowed`。
- 修复：资产名 `.app` → `.hap`（内容为 zip 格式包，后缀不改变格式，与 v2.1.1 及历史一致）。

## 3. 一个关键的验证陷阱（L52）

修完 `.app→.hap` 后调 `rerun-failed-jobs` 重跑 publish，**日志里 `files:` 仍是旧的 `...-ohos.app`**——`rerun`/`rerun-failed-jobs` 用的是该 run **创建时**的 workflow 定义，不读最新 YAML。只能把 tag 移到新 commit 强制触发新 run，新 run 才用上新 workflow。

## 5. 发行动作清单（可复用）

1. `pubspec.yaml` 版本号 bump；CHANGELOG `[Unreleased]` → `[x.y.z]` 并写发行说明。
2. 只暂存自己的文件（`pubspec.yaml`/`CHANGELOG.md`），别把工作区他人未提交改动 `git add .` 进来。
3. 提交 → 推 main → `git tag -f v<version>` 移到发行 commit → 推 tag（force）触发 release。
4. 用 token 查 run/job 状态与资产（匿名 API 有速率限制）。
5. 失败后按「job conclusion → 该 job 日志尾 → 判据」定位，别猜。
