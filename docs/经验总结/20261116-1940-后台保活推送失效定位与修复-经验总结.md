# 经验总结：后台保活「任务完成推送」失效的定位与修复

> 时间：2026-11-16 19:19–19:40　角色：主控（单会话）
> 关联计划：[20261116-1919-后台保活与任务完成推送失效-开发计划](../开发计划/20261116-1919-后台保活与任务完成推送失效-开发计划.md)
> 一句话：保活只保进程，不保 WebView JS；完成通知寄生在 JS 观察者上，后台 JS 被冻结即丢事件。Dart/原生无法绕过 JS 桥直连宿主，最终走「后台心跳唤醒 JS + 去重 + 文案如实化」。

## 1. 现象

用户反馈：应用切后台，任务完成后**没有收到推送**；点进应用重新连接后，通知才补发出来。

## 2. 定位过程（代码级探查，非真机先判）

派后台只读子智能体全仓扫「保活/推送/后台/通知/生命周期」链路，得到关键事实链：

1. 全仓无 FCM / 厂商推送 / 远程通知注册——所谓推送是 `flutter_local_notifications` 本地通知。
2. 唯一的完成通知调用点在 `session_view.dart:_onBridgeMessage`，依赖 WebView `callHandler('zrEvents')` 回传的事件。
3. 完成事件两条来源：宿主主动报文（`EventParser`）、本地 diff（`StateDiffer.apply`，`running→completedSuccess`）。
4. 保活 `KeepAliveService.kt`（前台服务 + PARTIAL_WAKE_LOCK）只维持进程存活；`state/keepalive.dart` 控制器仅在开关/设备/回前台时同步，**进后台不做任何事**。
5. `NotificationGate.shouldNotify` 后台放行，通知插件正常——断点不在「显示」，在「事件产生/回传」。
6. 回前台 `_onAppResume → _manualReload` 重载 WebView → 全量快照 → `StateDiffer` diff 出完成 → 补发。与用户现象完全吻合。

**结论**：事件是「回前台后才产生」的，不是「后台攒着没发」。误判高发点：一开始容易归咎于「保活没生效/通知权限」，实际两者都正常。

## 3. 关键转折：架构裁定否决了计划里的两个方向

原开发计划提了 D1/D2/D3/D4/D5 五个方向，其中 D2（Dart 侧独立轮询宿主）、D5（原生后台直连宿主）看似最根治。

**读真实代码后发现致命前提错误**：所有宿主数据访问都走同一条链——
```
RpcBridge.call() → LoopbackDispatchServer.push()
  → 注入 WebView 的 JS 从 http://127.0.0.1:<port>/zrp/<token> 拉命令
  → JS 调宿主服务 → callHandler('zrSvcResult') 回传 Dart
```
Dart 与 Android 原生**根本无法脱离 WebView JS 直接访问宿主任务状态**。D2/D5 的地基不存在，当场否决。

**教训**：写开发计划时基于「概念设计」提方向可以，但进入实施前必须读真实调用链验证前提；否则会把大量工时投在不可能落地的方案上。这正是 S2「反向验证成对」在方案选型上的延伸——先证伪，再投入。

## 4. 最终方案与实施

- **D1（核心）**：`BackgroundHeartbeatPolicy`/`BackgroundHeartbeat`（纯 Dart 策略，20s 周期）+ 注入 JS 暴露 `window.__zrKeepAliveTick()`（唤醒 `zrPollRevive` + 调 `windowControllerService.listTaskList()` 拉快照，按 `{result:{tasks}}` 经 `zrBgSnapshot` 回传）+ `session_view` 心跳定时器与独立 `_backgroundStateDiffer`，复用抽取出的 `_dispatchEvents` 弹通知。
- **D3**：`NotifiedEventStore`（shared_preferences 持久化，10min 窗口去重），防「后台心跳 / 前台链路 / 回前台补发」多链路对同一完成事件重复推送。
- **D4**：`keepAliveOn` 文案从绝对承诺改为「尽力而为/可能延迟」，中英 arb + gen-l10n。

## 5. 验证与真机走查（2026-11-16 补做）

- 静态/单测：注入 JS 语法 4 例 + node 语义 21 场景 + 新增单测 6 例（含反向验证）全过；全量 1222 例全绿；analyze 零问题。
- **CI**：推送 `bf514a9` 后 GitHub Actions 两条 workflow 均 `success`（用 SQL Visualizer 仓 `.local/github-token.json` 的 PAT 配 gh 查得）。
- **真机走查（设备上线后）**：构建 debug APK 装入模拟器并连上远程宿主（LED 绿、41 method-ok）。切后台证实：
  - D1 心跳 20s 周期触发（`bg tick` ×2/45s）、进程存活、保活通知正常、`evaluateJavascript` 后台可执行（`tick result=ok`）；
  - JS→Dart 的 `callHandler` 后台可用（诊断数据成功回传）；
  - **但宿主 `windowControllerService.listTaskList()` 抛 `ChannelClient is disposed`** —— 宿主后台主动 dispose 原生 RPC client，App 侧无法绕过。
- **端到端判定**：本环境下无法做到后台即时弹通知；可靠路径是 D3 去重 + 回前台补发（不丢）+ D4 文案如实（可能延迟）。D1 的"主动拉快照"保留为宿主 client 恰好存活时的尽力增强。

## 6. 结论与后续

- 真机走查把"后台即时推送"从推测坐实为**宿主侧限制**：callHandler 通、宿主业务 RPC 断（ChannelClient disposed）。三层链路要分层测（L39）。
- 若要真正后台即时推送，需宿主侧配合（后台不 dispose client / 提供服务端推送），属跨端立项，非本 App 能独立完成。
- 未覆盖 OEM/Doze 更激进机型（小米/vivo/鸿蒙），结果不泛化；iOS 无后台模式按文案声明不适用。
