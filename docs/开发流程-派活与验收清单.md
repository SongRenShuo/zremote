# 开发流程：派活与验收清单

> 本文是 `AGENTS.md` 第 3 条指向的作业细则：主控怎么派活、怎么交活、收口怎么验收。只写可执行动作，规则来自实际返工点（2026-11-14 功能工具箱修复战役实证）。

## 一、派活模板

每条派活必须写死以下六项，缺一项就会在现场临时猜：

1. **写集**：列出该车道会碰的文件/目录，保证互斥；多车道共写文件（如 `CHANGELOG.md`、l10n arb）提前说明冲突处理方式。
2. **只跑定向**：`flutter test test/<文件> --plain-name "<用例名>"`；**收口前必须全量** `flutter test` + `flutter analyze`（一个 unused_import 也会红 CI，L9）。
3. **长命令一律后台**：构建/测试/下载用后台任务启动，完成后按通知处理；**禁 sleep 轮询阻塞会话**（用户明确要求过）。后台任务的 stdout 日志落文件（`> /tmp/xxx.log`），报告引用读数时贴文件内容。
4. **提交纪律**：每完成一件可提交的就立即提交；提交 body 写「跑了什么测试、读数多少」；长 body 写文件 `-F`（S8）。
5. **报告字段**：改动文件、提交哈希、定向读数（N/失败/错误）、全量读数、未完成项与风险。没跑过的读数不许写「全绿」。
6. **失败即诊断**：CI 红 / 构建失败，先读「What went wrong 的异常消息本体」（判据见规范 E6），再决定动哪个缓存/组件；禁无证据乱改。

红线：不 push（除非用户授权）、不合流、不建 tag、不动 CI 工作流；改前先读 `docs/LESSONS.md` 与 `docs/规范/本机环境清单-规范.md`。

## 二、验收清单

1. **读数可复核**：读数要能对上 `flutter test` 输出行（`NN: +N: All tests passed!`）或 CI job 日志，不接受「全绿」两个字。
2. **反向验证**：解析容错类改动用「形状漂移 fixture」当反例（外壳包裹、字段缺失、类型漂移三类）；注入 JS 改动跑 `hook_script.test.mjs` 场景对照。
3. **not run 条款**：没跑的测试、真机走查逐项列「没跑 + 为什么」；模拟器验证不冒充真机验证。
4. **CI 判定**：推送后 CI 结果后台确认（轮询放后台任务）；红了先拉日志（`actions/jobs/<id>/logs`），按 E6 判据诊断，修复后**本地全量绿**再推。
5. **文档三件**：计划册状态与实施记录、`docs/索引/开发计划.md` 索引行、`CHANGELOG.md`（带提交哈希）；改注入 JS/服务契约的同批更新架构文档与 hook_script 测试场景。

## 三、常见坑（本轮实测）

- **Windows Git Bash**：`/X` 参数会被当路径转义（写 `.ps1`）；中文长文直传易乱码（写文件）；`flutter.bat`/`adb.exe` 都用全路径。
- **properties 文件反斜杠**：`sdk.dir=D\:\\HuanJing\\...` 的转义按 Java Properties 规则解析，写错会导致 Gradle 找不到 SDK——改完用 `flutter doctor` 回读验证。
- **后台任务日志**：`flutter run` 类长驻进程 stdout 要落文件再 tail，后台任务的流式输出对 grep 不友好。
- **同一个 testWidgets 里二次 pumpPage**：同类型 widget 走 didUpdateWidget 复用 State，需要"重新初始化"的场景必须拆用例（L6）。
